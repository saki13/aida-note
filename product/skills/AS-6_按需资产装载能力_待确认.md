# AS-6 按需资产装载能力规则

> 版本：v0.1.0
> 资产归类：产品资产 -> SKILL 能力规则
> 对应 Backlog：`AS-6` 按需资产装载能力（含 context_cache）
> 作用：定义 M9 资产装载模块的行为规则--在启动恢复、任务切换、阶段切换时，如何精确供给任务上下文，使 Aida 不依赖长会话历史即可正确执行当前任务。

## 1. 设计目标

AS-6 定义 M9 资产装载模块的行为规则。M9 的核心使命是**任务上下文供给**：确保 Aida 在执行任何任务时，携带正确的任务上下文（skill、rule、SIS、资料），而不是依赖长会话历史。

这一能力的价值：

1. **新会话即用**：通过 memory 恢复 + cache 供给，新会话无需历史对话即可工作
2. **注意力聚焦**：只装载当前任务需要的上下文，减少无关信息干扰和幻觉
3. **经济高效**：不依赖百万级上下文窗口，降低 token 消耗和延迟
4. **随时重启**：可随时开启新会话，通过结构化记忆快速恢复到正确状态

### 1.1 管什么

- 任务上下文的识别：当前任务需要哪些上下文
- 任务上下文的供给：从 cache 或全文中装载所需上下文
- 任务上下文的切换：任务/阶段变化时，切换到新任务所需的上下文
- 缓存的批量更新：工作流结束后统一刷新 stale 缓存条目

### 1.2 不管什么

- LLM 会话上下文管理（多轮对话历史累积，由 LLM 性质决定）
- 子 agent 派活时的上下文打包（待后续实现自动派发时再覆盖）
- 缓存结构设计（由 AS-6-Cache 定义）
- 模块级上下文提取表（由 AS-6-Cache 第 7 节定义，本文件引用）

## 2. M9 模块定位

### 2.1 在 AS-9 分层中的位置

M9 属于 AS-9 第 3.3 节工作模块层（L3），对应协议与资产层（L4）的读写网关。

### 2.2 角色性质

M9 是**服务型模块**，不直接产出业务结果，而是为其他工作模块（M1-M14）提供上下文供给服务。

### 2.3 双模式运行

M9 有两种运行模式：

| 模式 | 触发时机 | 核心动作 |
|------|---------|---------|
| 启动模式 | 新会话恢复 | 按 manifest 装载顺序 + context_cache 执行装载 |
| 按需模式 | 任务切换、阶段切换 | 增量装载新任务/新阶段所需的上下文 |

正常工作流执行中（同一任务同一阶段内），M9 一般不需要触发--启动时已装载的上下文通常足够。

---

## 3. 启动模式

### 3.1 装载流程

启动模式的装载流程遵循 AS-6-Cache 第 6 节定义的流程，M9 的职责是执行该流程：

```
1. 读取 manifest.md
   -> 获取当前状态、任务、装载清单
2. 读取 state.md
   -> 获取状态快照
3. 读取 decisions.md
   -> 获取近期决策
4. 读取 context_cache.md
   -> 获取所有缓存摘要
   -> 逐条检查 last_updated，标记 stale 条目
5. 读取 SKILL 全文
   -> 执行载体，不使用缓存，必须全文装载
6. 对 manifest 清单中剩余资产：
   -> 缓存命中且非 stale -> 跳过全文装载
   -> 缓存 miss 或 stale -> 按需全文装载
7. 装载完成后：
   -> 若缓存不存在，生成首次 context_cache.md
   -> 若有 stale 条目已回源，更新对应缓存条目
```

### 3.2 无缓存时的回退

当 context_cache.md 不存在时：

1. 不阻断恢复流程
2. 跳过缓存步骤，按 manifest 装载顺序逐个读取全文
3. 装载完成后，自动生成首次 context_cache.md

### 3.3 上下文预算不足时的降级

当上下文预算紧张时，按以下优先级保留（引用 AS-6-Cache 第 6.3 节）：

| 优先级 | 保留内容 |
|--------|---------|
| P0 | manifest + state + decisions |
| P1 | SKILL 全文 |
| P2 | context_cache 全部摘要 |
| P3 | 工作流图全文 |
| P4 | 治理规则全文（按需回源） |
| P5 | Backlog 全文（按需回源） |
| P6 | AS 系列全文（按需回源） |

## 4. 按需模式

### 4.1 触发场景

按需模式在以下场景触发：

| 场景 | 触发条件 | 说明 |
|------|---------|------|
| 任务切换 | 一个 backlog 项完成后，启动下一个 | 新任务可能需要不同的 skill、rule、SIS |
| 阶段切换 | 工作流阶段发生变化 | 不同阶段需要的上下文类型不同 |

### 4.2 任务切换装载

完成一个 backlog 项后启动下一个时，M9 执行以下步骤：

1. **识别新任务类型**：从 manifest 的 Sprint 任务清单中读取下一个任务的 ID 和名称
2. **确定所需上下文**：根据任务类型，确定需要哪些 skill、rule、SIS、资料
3. **查缓存命中**：检查 context_cache 中对应条目是否命中且非 stale
4. **增量装载**：对 miss 或 stale 的条目，回源全文装载
5. **更新任务追踪**：在 state.md 中更新当前任务

### 4.3 阶段切换装载

阶段切换时，M9 按以下映射表执行增量装载。先查缓存命中，miss 或 stale 才回源全文。

| 阶段切换 | 需要新装载的上下文 |
|---------|-------------------|
| -> Backlog Grooming | Backlog 全文、PCB |
| -> Planning Input Ready | Backlog 全文、反思结论（若有） |
| -> Planning | Backlog 全文、候选项清单、Sprint 启动文档模板 |
| -> Sprint In Progress | Sprint 启动文档、当前任务详情、SKILL |
| -> Sprint Completed | 交付物清单、DoD 定义、审计轨迹 |
| -> Review | Sprint 启动文档、DoD、交付物、审计轨迹 |
| -> Retrospective（可选） | Review 报告、Pulse Sync 事件日志 |
| -> 下一轮 Planning | 反思结论、Backlog 最新状态 |

### 4.4 装载决策逻辑

```
对于每个需要的上下文项：
  IF context_cache 中存在该条目 AND 非 stale
    -> 使用缓存摘要，跳过全文装载
  ELSE IF context_cache 中存在该条目 AND stale
    -> 回源全文装载，装载后更新缓存条目
  ELSE IF context_cache 中不存在该条目
    -> 回源全文装载，装载后新增缓存条目
  ELSE IF 源文件不存在
    -> 暴露问题：所需资产缺失，不继续推进
```

## 5. 上下文充分性检查

### 5.1 混合检查策略

采用混合策略判断上下文是否充分：

| 模块类型 | 检查方式 | 适用模块 |
|---------|---------|---------|
| 关键模块 | 硬清单检查 | M1 阶段识别、M6 分流、M7 回写、M12 DoD 评估 |
| 其他模块 | 自省判断 | M2/M3/M4/M5/M8/M10/M11/M13/M14 |

### 5.2 硬清单检查规则

关键模块执行前，M9 按以下清单检查上下文是否就位（引用 AS-6-Cache 第 7.2 节）：

| 模块 | 必须就位的上下文 | 缺失时行为 |
|------|---------------|-----------|
| M1 阶段识别 | 当前阶段（state）、阶段定义（工作流图）、阻断条件（G5） | 调 M9 装载，不装载完不执行 |
| M6 结论分流 | 会议结论（输入）、分流规则（AS-4）、Backlog 引用 | 调 M9 装载，不装载完不执行 |
| M7 会后回写 | 分流结果（M6 输出）、回写目标（AS-5）、Backlog 当前状态 | 调 M9 装载，不装载完不执行 |
| M12 DoD 评估 | DoD 定义（Sprint 文档）、实际产出（交付物） | 调 M9 装载，不装载完不执行 |

### 5.3 自省判断规则

非关键模块执行时，Aida 通过自省判断上下文是否充分：

1. 是否理解当前要做什么
2. 是否知道输入从哪里来
3. 是否知道输出到哪里去
4. 是否知道适用的规则是什么

若任一项为"否"，触发 M9 按需装载。

### 5.4 装载失败处理

当 M9 无法装载所需上下文时（源文件不存在、路径错误等）：

1. 显式暴露问题：说明缺什么、为什么缺
2. 不硬推进入下一步
3. 给出补救建议：创建缺失文件、修正路径、或向 PO 询问

## 6. 缓存更新

### 6.1 更新时机

采用批量更新策略：工作流执行中只标记 stale，在工作流结束时统一刷新。

### 6.2 更新流程

```
工作流执行中：
  每次回写文件后 -> 标记 context_cache 中对应条目为 stale

工作流结束时（Step 11 更新运行状态之后）：
  M9 批量刷新所有 stale 条目：
    1. 重新读取源文件
    2. 重新生成摘要
    3. 更新 last_updated 时间戳
    4. 清除 stale 标记
    5. 写入 context_cache.md
```

### 6.3 中断恢复

若工作流中途中断（会话结束、异常等），stale 条目保留。下次新会话恢复时：

1. M9 在启动模式中检测到 stale 条目
2. 回源全文并更新缓存
3. 不会丢失信息

工作流图中每个阶段切换节点，隐含触发 M9 的按需模式。AS-6 不修改工作流图，只定义 M9 在阶段切换时的行为。

## 8. 当前阶段不做什么

- 不做子 agent 派活时的上下文打包（待自动派发能力实现时再覆盖）
- 不做 LLM 会话上下文管理（多轮对话历史由 LLM 管理）
- 不做自动文档变更检测（依赖 Aida 在回写时主动标记 stale）
- 不做上下文预算精确计量（LLM 无法精确测量，用降级策略替代）
- 不做缓存压缩算法优化（由 AS-6-Cache 的固定 token 上限控制）
- 不修改 SKILL 的 12 步工作流（AS-6 是服务型模块，被调用而非嵌入流程）

## 10. 结论

M9 资产装载模块是 Aida 从"靠对话驱动"升级为"靠资产驱动"的关键能力。它通过精确的任务上下文供给，让 Aida 在任何新会话中都能快速恢复到正确的工作状态，不依赖长会话历史。

核心设计哲学：**用结构化记忆和按需装载替代百万级上下文窗口。每次任务执行只携带必要的上下文，保持注意力聚焦，减少幻觉，提高效率。这是未来 Agent 应有的工作模式。**
