# G5 流程守门与阻断机制

> 版本：v0.1.0
> 资产归类：产品资产 -> 治理规则
> 对应 Backlog：`G5` 流程守门与阻断机制
> 依赖：`AS-1`（阶段识别与流程守门规则）、`Aida 职责边界总规则 v0.1.0`
> 作用：定义各阶段的准入/阻断条件、补救路径和事件处理模板，确保 Aida 独立运行时不会因守门过软而失控，也不会因守门过重而卡死流程。
> 上级文档：[AidaPulse 白皮书 v0.1.0](../whitepaper/AidaPulse白皮书_待确认.md) 第 10 节

---

## 1. 设计原则

v0.1.0 采用**简化阻断策略**：系统不需要过多卡点。只有在最基础的准入条件不满足时才硬阻断，其他阶段的问题通过流程自身消化（如回流 Backlog、补写报告等）。

核心思路：
1. **仅 Backlog Grooming 设硬阻断**：项目级纲领缺失时才卡住
2. **其余阶段不设卡点**：问题通过流程自身消化
3. **阻断必须有补救路径**：阻断不是终止，而是"先补什么再继续"

---

## 2. 与 AS-1 的关系

`AS-1` 定义了阶段识别能力和三档守门动作（提醒、异议、阻断），偏"认知框架"。`G5` 在此基础上做三件事：

1. **把阻断条件写死**：不再是"输入不足时提醒"，而是"以下字段缺失时硬阻断"
2. **把补救路径写死**：阻断后不只是"回到上一步"，而是"回到哪个具体动作、补什么"
3. **把短 Sprint 的准入写死**：什么时候能开短 Sprint

---

## 3. 各阶段阻断条件与处理方式

### 3.1 Backlog Grooming（硬阻断）

**这是唯一设硬阻断的阶段。**

**硬阻断触发条件**（满足任一即阻断）：

| 条件 | 说明 |
|------|------|
| 无初始 PCB | 项目级纲领缺失，无法建立全局理解 |
| 无初始 Backlog | 无可排序的工作项池 |
| 无未决议题记录 | Grooming 过程中有未决事项但未记录 |

**阻断动作**：
- 声明当前阶段为 `Backlog Grooming`
- 声明阻断级别为 `stage_blocked`
- 明确指出缺失项
- 指出补救方向：先补齐 PCB / Backlog / 未决议题
- 阻止进入 Planning

**补救路径**（缺什么按模板生成什么）：

```
缺失 PCB -> Aida 按模板自动生成最小 PCB（项目目标、核心角色、术语表）
缺失 Backlog -> Aida 准备问卷加速收敛，收集并排序至少 5-10 个候选项
缺失未决议题 -> Aida 记录未决事项到未决议题池
```

---

### 3.2 Planning（仅"无任务池"阻断）

**阻断条件**：

| 条件 | 说明 | 处理方式 |
|------|------|---------|
| 无可用任务池 | Backlog 中无可选取的候选项 | PO 确认无新任务 = 项目完成；否则回到 Grooming 扩充 |

**不阻断的情况**（直接继续 Planning）：
- 未锁定正式输入 -> 用三级收敛（正式/候补/暂缓）重新整理
- 未产出启动文档 -> 先写 Sprint 启动收口再结束 Planning
- 存在不可执行项 -> 把该项退回候补或暂缓，重新检查正式输入

---

### 3.3 Sprint（无阻断）

**无阻断条件。**

遇到问题时的处理方式：
- 通过 **Pulse Execution Sync** 机制异步广播事件通知
- 触发条件：任务执行完成通知、资源告警、风险通告、出现卡点需要人工清障、SIS 执行状态更新
- 由 PO 决定是否介入

---

### 3.4 Sprint Completed（无阻断）

**无阻断条件。**

Aida 自主动作：
- 检查交付完整性
- 发起 Review

---

### 3.5 Review（无主动阻断）

**无主动阻断。**

未通过项的处理方式：
- 未通过项回流到下次 Planning 或 Retrospective
- 结论必须写，没写 Aida 自己补

**不阻断的情况**（通过流程消化）：
- 无交付成果可展示 -> 先补齐本轮 Sprint 执行再开 Review
- 未对照 DoD -> 先逐项检查并形成对照表
- 未通过项无去向 -> 对每个未通过项明确：退回 Backlog / 阻塞处理 / 等待决策
- 未产出结论 -> Aida 先写正式 Review 报告

---

### 3.6 Retrospective（可选，无主动阻断）

**触发条件**：Aida 觉得 Sprint 中有做的不好的、需要讨论的问题，通知 PO 建议开启反思会。PO 认可后才走此流程。

**无主动阻断。**

未形成有效结论时的处理方式：
- 把问题作为待完善项加入 Backlog
- 不需要卡点

---

### 3.7 Planning Input Ready（无阻断）

**无阻断条件。**

Aida 自省阶段，无人类干预。只要有 Backlog 就可以进入 Planning。

## 4. 短 Sprint 准入

短 Sprint 的"短"体现在**时间维度**上，不是限制任务数量。因为全部采用 AI 开发，Aida 可全程自主检查评估，可连续开启，执行效率高。

**准入条件**（必须全部满足）：

| 条件 | 说明 |
|------|------|
| PO 明确授权 | PO 口头或书面同意开启短 Sprint |
| Backlog 明确 | 任务范围清晰 |
| 高内聚的需求集合 | **不限制任务数量** |
| AI 可自主评估的 DoD | DoD 有可验证的标准 |

**不满足时**：
- 声明准入条件不满足
- 声明不能以短 Sprint 模式开启
- 建议转长 Sprint 或补齐准入条件后再申请

---

## 5. 阻断事件的标准处理模板

每次触发硬阻断时，Aida 必须产出以下结构：

```markdown
## 阻断通知

- `阻断编号`：`block-<YYYYMMDD>-<序号>`
- `阻断时间`：
- `当前阶段`：
- `阻断级别`：`stage_blocked`
- `触发条件`：具体触发了哪条阻断条件
- `缺失项`：缺什么
- `影响范围`：如果不处理会怎样
- `补救路径`：需要先去补什么、怎么补
- `补救完成后可进入`：补完后下一阶段是什么
- `已通知角色`：PO / PC
```

---

## 6. 守门与记忆系统的联动

阻断事件必须同步更新记忆系统：

- `manifest.md`：更新 `current_stage` 为对应的 `_blocked` 状态
- `decisions.md`：记录阻断决策
- 阻断通知写入审计轨迹

阻断解除后，同步恢复 manifest 中的状态。

---

## 7. 当前不做什么

- 不做自动升级机制（多次阻断后自动通知 PO--这依赖通知系统更成熟）
- 不做阻断统计面板
- 不做阻断超时自动转长 Sprint
- 不做复杂依赖关系检查
