## 1. 规则定位

本规则用于定义 AidaPulse 在当前阶段的会议治理总框架。

它回答四个核心问题：

1. AidaPulse 中有哪些核心会议 / 流程。
2. 每类会议在什么情况下触发、如何推进、何时结束。
3. 所有会议结束后，必须沉淀哪些统一产物。
4. Aida 如何作为流程中枢，确保会议规则被真正执行。

本规则优先追求：

- 简单可执行
- 不轻易跳过流程
- 允许柔性迭代
- 支持后续工具化、Skill 化与产品化

---

## 2. 会议治理原则

### 2.1 流程正义优先

- 会议可以简化，但不应随意跳过必要流程。
- 任何阶段的进入都应满足相应前提条件。
- 如果检查机制未通过，应优先补材料、补结论、补规则，而不是强行推进。

### 2.2 会议服务于项目推进

- 会议不是为了保留 Scrum 形式而存在。
- AidaPulse 中的会议应服务于：
  - 澄清目标
  - 选择工作项
  - 暴露阻塞
  - 促进交付
  - 形成沉淀
  - 推动系统进化

### 2.3 所有会议必须留下资产

- 会议不能只停留在对话里。
- 所有会议至少要形成统一最小输出集合，并在必要时回写到项目资产中。

### 2.4 Aida 是会议治理执行中枢

- 当前阶段，Aida 是 AidaPulse 会议治理的核心执行中枢。
- Aida 负责会前检查、会中辅助、会后沉淀、流程提醒与必要阻断。
- 但 Aida 不能替代人类角色做价值优先级、需求取舍、高风险接受、额外资源投入和项目边界变化等决策。

---

## 3. 核心会议 / 流程清单

当前阶段，AidaPulse 采用以下五类核心会议 / 流程：

1. `Backlog Grooming / 待办事项整理会`
2. `Planning / 计划会`
3. `Pulse Execution Sync / 脉冲执行同步`
4. `Review / 评审会`
5. `Retrospective / 反思会`（可选）

当前不单独把“风险升级会”定义为第六类标准会议。

风险、阻塞、升级和资源协调优先消化在以下机制中：

- `Pulse Execution Sync`
- `Review`
- `Retrospective`

如后续实践证明必要，再单独抽象为专项会议类型。

## 4. 各类会议总规则

### 4.1 Backlog Grooming / 待办事项整理会

**会议定位**

- 项目启动阶段最关键的基础会议之一。
- 核心目标不是估算工作量，而是整理项目背景、原始需求、团队认知和初始边界，形成可治理项目输入。

**触发条件**

- 项目刚启动，`PO` 已掌握初步业务背景和外部输入材料。
- 或项目后续发生重大变化，原有 `Backlog` 与背景判断不足以支撑后续迭代。

**必须参与角色**

- `PO`
- `Aida`

**可选参与角色**

- `PC`
- `PT` 代表

**会议重点**

- 梳理项目背景与目标
- 澄清需求与初始边界
- 形成初始 `PCB`
- 形成初始 `Backlog` 池
- 形成项目规范初稿
- 记录未决议题

**本会议不做什么**

- 不进行详细工作量估算
- 不强行把需求一次性拆到过细
- 不要求当场解决所有问题

**结束条件**

- 初始 `PCB` 已形成
- 初始 `Backlog` 池已形成，且达到“可以执行”的最低要求
- 项目规范初稿已形成
- 未决议题已被记录
- Aida 会后检查通过，或明确提出异议

### 4.2 Planning / 计划会

**会议定位**

- 用于明确下一次 Sprint 的任务范围。
- 同时承担“补充和修正 Backlog”与“选取任务进入 Sprint”的职责。

**模式区分**

- 长 Sprint Planning
- 短 Sprint Planning

**触发条件**

- 首次 Planning：`Backlog Grooming` 结束后，由 `Aida` 整理 Backlog 并提醒 `PO` 召开。
- 后续长 Sprint Planning：上一轮 `Review` 或 `Retrospective` 结束后，由 `Aida` 提醒 `PO` 召开。
- 短 Sprint Planning：在 `PO` 已授权连续短 Sprint 的前提下，由 `Aida` 自行触发。

**必须参与角色**

- `Aida`
- 长 Sprint 场景下，未授权时 `PO` 必须参加

**会议重点**

- 汇报项目进度与 Backlog 状态
- 识别待补材料与待拆分项
- 更新 Backlog
- 选择本轮 Sprint 任务
- 评估工作量
- 形成会议纪要与 Sprint 任务清单

**不得进入 Sprint 的 Backlog**

- 未通过检查条件
- 不具备执行前置条件
- 需求不明
- 仍需 `PO` 参与设计
- 依赖外部关键资源且未准备完成
- 材料缺失、边界不清、验收标准不明

**短 Sprint 的附加规则**

- 准入标准：PO 明确授权 + Backlog 明确 + 高内聚需求 + AI 可自主评估 DoD
- 任务必须足够明确
- 必须具备可自动检查的完成条件
- AI 可自主评估 DoD
- 短 Sprint 不限制任务数量，只要是高内聚的需求都可以加入。“短”体现在时间维度上——因为全部采用 AI 开发，Aida 可全程自主检查评估，可连续开启，执行效率高，从而可以快速完成

**结束条件**

- 已有一批足以支撑本轮 Sprint 的 Backlog 被正式选入
- Aida 已完成 Sprint 任务池整理
- 已形成会议纪要与任务清单

### 4.3 Pulse Execution Sync / 脉冲执行同步

**流程定位**

- 这是传统 `Daily Scrum` 在 AidaPulse 中的演进形态。
- 本质上是 AidaPulse 的“新 Daily Scrum”：
  - Aida 主导的异步状态同步机制
  - 遇到阻塞时的执行协调机制
  - 项目推进过程中的实时可视化与纠偏机制

**触发条件**

- 任务状态变更
- 任务阻塞
- 依赖缺失
- 风险升高
- 需要人类介入
- 单条 Backlog 完成
- Aida 派发补位任务
- Sprint 即将到期
- 关键节点完成

**参与方式**

- 默认异步
- 必要时拉同步小会
- 短 Sprint 中，Aida 可先组织 `2-3` 轮 Agent 自动排障
- 达到轮次上限后，必须升级给 `PO` 和 `PC`

**核心作用**

- 暴露阻塞
- 广播进度
- 更新看板与过程记录
- 触发纠偏与资源协调

### 4.4 Review / 评审会

**会议定位**

- 核心作用与传统 Scrum 基本一致：
  - 展示交付成果
  - 判断任务是否完成
  - 收集 `PO` 反馈
  - 判断哪些 Backlog 可以关闭
  - 决定哪些内容退回修正

**模式区分**

- 长 Sprint Review：人类正式参与
- 短 Sprint Review：由 `Aida` 自动完成并抄送 `PO`

**触发条件**

- 一个 Sprint 正常结束
- 短 Sprint 结束时也必须有评审动作

**必须参与角色**

- `Aida` 始终必须参加
- 长 Sprint 下：
  - `PO`
  - 若有 `PC` 则必须参加
  - `PT` 代表必须参加
  - 若 `PT` 中存在测试型 Agent，则该 Agent 应参加评审

**未通过项处理**

- 重新回到 `Backlog`
- 若伴随阻塞，则进入 `Pulse Execution Sync` 机制处理

### 4.5 Retrospective / 反思会

**会议定位**

- 面向流程、协作、工具、质量和规则的系统复盘会议。
- 它不是形式化仪式，而是进入下一轮 `Planning` 前的重要治理节点。

**触发条件**

- Aida 觉得 Sprint 中有做的不好的、需要讨论的问题（未完成、效果不理想等），通知 PO 建议开启反思会。PO 认可后才走此流程

**必须参与角色**

- 全体相关成员

**关键原则**

- 未形成有效结论时，把问题作为待完善项加入 Backlog 或在原 Backlog 上修改。不需要卡点，系统不需要那么多阻断。

**核心作用**

- 输入：Pulse Execution Sync 事件日志作为决策辅助依据
- 复盘流程、协作、工具、质量问题
- 形成改进项
- 识别规则修订项
- 识别 `Skill` 候选项
- 沉淀新增 `Backlog`

## 5. 所有会议的统一输出规则

### 5.1 最小输出集合

所有会议至少应具备以下最小输出：

- 会议纪要
- 决议事项
- 未决议题
- 责任人与后续动作
- 是否需要更新 `Backlog`
- 是否需要生成或更新 `SIS`

### 5.2 会议纪要标准字段

**必填字段**

- 会议名称
- 会议类型
- 会议时间
- 参会角色
- 核心结论
- 决议事项
- 未决议题
- 回写动作
- 下一步行动项

**可选字段**

- 会前输入材料
- 相关 `Backlog ID`
- 相关 `SIS ID`
- 风险摘要
- 备注

### 5.3 回写动作定义

回写动作指会议结束后，需要把结论同步更新到哪些项目资产以及如何更新，例如：

- 更新 `Backlog`
- 新建或更新 `SIS`
- 写入未决议题池（按照 [G3 未决议题池管理规则](G3_未决议题池管理规则_待确认.md)，Backlog 即议题池）
- 更新过程文档
- 更新看板内容

### 5.4 SIS 输出原则

- 所有 `Backlog` 都伴生一个 `SIS`
- 其他任何需要传递给 Agent 的关键信息，也应尽量以 `SIS` 形式记录
- `SIS` 是系统内部所有 AI 的标准输入输出格式

### 5.5 Backlog 更新原则

当前阶段先不把“哪些会议必须更新 Backlog”写成僵硬规则，但以下会议通常会自然触发 Backlog 更新：

- `Backlog Grooming`
- `Planning`
- `Review`
- `Retrospective`
- `Pulse Execution Sync`（发生状态变化时）

## 6. 未决议题治理规则

> 详细规则见 [G3 未决议题池管理规则](G3_未决议题池管理规则_待确认.md)，本节仅保留治理层面的结论。

### 6.1 核心设计

- **Backlog 即议题池**：不创建独立的 `project/issues/` 文件，未决议题是 Backlog 中的一条记录
- **标记方式**：在 Backlog 条目标注 `未决`/`讨论中`/`defined`/`resolved` 状态
- **扩充字段**：增加 `owner`（落实人）字段，未决时可为空，PO 指定后填入
- **生命周期**：提出（未决）→ Planning 中被 PO 提起 → PO 补充 owner/dod/sis（或关闭/暂缓）→ 下次讨论或执行

### 6.2 Aida 的刚性要求

- `Aida` 必须在每次 `Planning` 开场时主动扫描并列出 Backlog 中所有 `未决`/`讨论中` 状态条目
- PO 逐项决策：补充（→`defined`）/ 关闭（→`resolved`）/ 暂缓（保持 `open`）
- 超 2 个 Sprint 仍在 `open` → Review 时标记为"长期未决"
- 超 3 个 Sprint → 建议 PO 明确关闭或指定 owner

## 7. Aida 在会议治理中的统一职责

### 7.1 会前

- 收集输入材料
- 做会前检查
- 预热资料
- 生成会前辅助包
- 提醒 `PO` 是否具备开会条件

### 7.2 会中

当前阶段主要承担：

- 会议辅助者
- 记录者
- 质疑和澄清提示者
- 有限参与的流程守门者

### 7.3 会后

必须完成闭环：

- 汇总会议结论
- 形成会议纪要
- 回写 `Backlog`
- 生成或更新 `SIS`
- 更新未决议题池（Backlog 中的未决状态项，按 G3 规则）
- 更新过程文档
- 更新看板
- 提醒相关角色后续动作
- 开启下一流程

### 7.4 必须提出异议或阻断的场景

- Backlog Grooming 阶段：缺少 PCB / Backlog / 未决议题时硬阻断
- Planning 阶段：仅“无任务池”为阻断条件（PO 确认无新任务 = 项目完成）

其他阶段不设主动阻断：
- Sprint 执行阶段：遇到问题通过 Pulse Execution Sync 通知，由 PO 决定是否介入
- Review：未通过项回流到下次 Planning 或反思会，结论必须写
- Retrospective：未形成有效结论则加入 Backlog

### 7.5 不得替代人类拍板的事项

- 价值优先级拍板
- 最终需求取舍
- 是否接受高风险方案
- 是否投入额外资源
- 是否改变项目边界

## 8. 阶段推进规则

当前阶段，AidaPulse 的会议推进应遵循以下主链路：

1. `Backlog Grooming`
2. `Planning`
3. `Pulse Execution Sync`
4. `Review`
5. `Retrospective`
6. 下一次 `Planning`

其中：

- 某些会议可能在特定场景下被简化，但其核心治理作用不得缺失
- 短 Sprint 需满足准入条件：PO 授权 + Backlog 明确 + 高内聚需求 + AI 可自主评估 DoD

---

## 9. 当前阶段的实施说明

本规则是 AidaPulse 在当前阶段的会议治理基线。

它不意味着：

- 所有细节都一次性定死
- 当前就具备全部自动化能力
- 当前就要把所有规则产品化

它意味着：

- 后续所有会议和相关资产沉淀，都应优先遵循这套总规则
- 新发现的问题，优先通过补充治理规则、模板、检查机制和 Aida 能力定义来持续完善
