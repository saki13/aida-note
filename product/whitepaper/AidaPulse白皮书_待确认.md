## 1. 愿景与核心理念 (Vision & Core Concepts)

传统的敏捷开发如同巨大的齿轮机械，人类在长达 2-4 周的 Sprint 周期中被固定节拍束缚。在 AI 时代，秒级的代码生成能力与周级的管理周期产生了严重错配。

**AidaPulse (AI-Driven Agile Pulse)** 应运而生。它脱胎于 Scrum，但抛弃了历史包袱，旨在建立一套真正适应 AI 时代的开发范式。它通过引入核心智能枢纽（Aida）与脉冲式迭代机制（Pulse），实现**超快速迭代、拥抱模糊需求、全面 AI 赋能**。

AidaPulse 的三大护城河：
1. **绝对的商业价值锚点（防止失控）**：PO 必须是人类，确保所有极速运行的 AI 任务始终服务于真实的商业目标。
2. **极度抽象的包容性（拥抱进化）**：不绑定特定大模型或工具，通过标准化的"结构化指令集 (SIS)"与看板契约，包容任何形态的 AI 开发者。
3. **落地为王与工具驱动（技能沉淀）**：每次开发与反思都将沉淀为可被工具读取的 `SKILL`（技能模块），使整个系统像有机体一样不断进化。

在 AidaPulse 中，**SIS 是框架级的主要任务数据形式**。所有服务于框架的 AI Agent，无论属于 Aida 还是 Pulse Team，都应能够接收 SIS 作为输入任务，并基于 SIS 理解 Backlog 内容、执行任务、反馈状态或推进流转。与此同时，SIS 必须能够被可视化渲染到敏捷面板中，使人类成员可以直接理解机器侧的结构化任务。

## 2. AidaPulse 敏捷宣言 (Manifesto)

我们在重塑软件开发的实践中，发现了更好地整合人类创造力与 AI 生产力的方法。由此，我们更看重：

1. **人与 AI 的智能分工与协作** 胜于 传统的流程与工具。
2. **持续交付可用的软件** 胜于 繁冗的文档（但结构化的文档和看板是人机沟通的核心基石）。
3. **始终在脉冲间拥抱内外变化** 胜于 僵化遵循既定计划。
4. **沉淀 Skill 赋能系统进化** 胜于 依赖个人的经验主义。

## 3. 四大核心角色 (Roles)

传统的 3 个角色演进为 **"3+1"** 模式，引入了核心 AI 枢纽。

### 3.1 产品负责人 (Product Owner, PO) -- 【人类】

- **核心定位**：商业价值的守护者，防止架构失控的风筝线。
- **职责**：定义产品功能与愿景，对投入产出负责。管理并排序 Product Backlog，决定发布内容与日期。认同或拒绝迭代交付。
- **AI 授权**：在"稳定开发阶段"且 Backlog 明确时，可短暂将执行权委托给 Aida，触发极速的"短 Sprint 脉冲"。

### 3.2 脉冲教练 (Pulse Coach, PC) -- 【人类 / AI / 缺席】

- **核心定位**：流程教练与清道夫。
- **职责**：不分配任务、不考核。指导团队遵循 AidaPulse 原则，排除障碍，保护团队免受外部干扰，促进团队多职能与高效运转。

### 3.3 Aida 项目编排者 (Aida Orchestrator) -- 【纯 AI Agent】

- **核心定位**：AI-Driven Agile 架构的"神经中枢"，以结构化项目输入为统一入口的流程执行中枢。

#### 3.3.1 角色本质

Aida 是整个 AidaPulse 的**节奏驱动者**，作为项目经理主导整个开发流程的推进工作。

核心使命：
- 保证整个 AidaPulse 工作流持续推进
- 通过不停迭代优化，将需求列表所有需求转化成 Backlog 并执行
- 通过迭代不停与 PO 丰富及变更需求，转化成 Backlog 和 SIS 在 Sprint 中执行
- 直到燃尽所有 Backlog，交付出客户满意的软件产品
- 在 PO 授权并且 Backlog 明确的条件下，通过独立主导短 Sprint 连续执行快速燃尽 Backlog 推进进度，并同步通知执行中的各种事件
- 调用 Aida 本身或其他我们定义的专项 Agent 自动执行 SIS

Aida 不是全能会议助手，也不是正式产品，而是：
- 一个以结构化项目输入为统一入口的原型机
- 一个按既有治理规则推进流程的流程执行中枢
- 一个能够留下关键审计证据并支持后续审查的原型载体
- 一个能从"靠对话驱动的助手"升级为"靠资产驱动的流程中枢"的 AI Agent

#### 3.3.2 四层能力模型

Aida 的能力分为四层，自底向上叠加：

| 层级 | 能力 | 说明 |
|------|------|------|
| Layer 1 | 自主状态恢复 | 通过记忆系统（L1 manifest）在新会话中恢复工作状态，按序装载资产 |
| Layer 2 | 流程识别与自主推进 | 根据当前阶段状态机判断是否需要发起动作，主动推进流程 |
| Layer 3 | 标准会议主导 | 按既有议程定义，独立主持 Planning / Review / Retrospective 三种核心会议 |
| Layer 4 | DoD 自动评估 | 读取 Sprint 启动文档中的 DoD 定义，逐项对照实际产出做通过/不通过判断 |

#### 3.3.3 核心能力清单

**输入与场景识别**：
- 识别当前属于哪类工作场景（会议型/收尾型/审查型/反思型/短脉冲事件型）
- 若当前场景不明确，只允许先做一次"场景确认式追问"
- 若当前场景与用户输入方式不匹配，必须先显式纠偏

**流程守门**：
- 判断当前阶段是否允许继续处理
- 检查准入条件是否满足
- 遇到阻断条件时主动停止并通知 PO，不硬推
- 阻断事件同步更新记忆系统

**处理链**：
- 建立处理链（生成 trace_id）
- 检查输入是否具备最小处理基础
- 只对关键缺口发起一轮问题组追问
- 对每条关键结论判断去向（SIS / Backlog / 未决议题池 / 过程记录）

**回写与通知**：
- 执行资产回写计划（Backlog / SIS / 未决议题池 / 过程记录）
- 向 PO 生成异步通知摘要
- 视情况向 PC / PT 生成提醒摘要

**审计与留痕**：
- 记录关键判断、关键动作和关键去向
- 记录阻断、异常和部分失败
- 支持后续 Audit Review 和 Critic Review

**自主行为**：
- 完成状态恢复后，根据当前阶段主动判断下一步动作
- 每次完成一个任务后，先回核主事实源，再启动下一个
- 连续推进超过 3 个任务且无重大决策点时，停下来向 PO 同步进度

**会议主持**：
- Planning：开场 -> 候选收集 -> 三级收敛 -> 顺序确认 -> 产出启动文档 -> 回写
- Review：开场 -> 回顾承诺 -> 汇报交付 -> 审查式清单 -> PO 反馈 -> Backlog 处理 -> 决定下一步
- Retrospective：开场 -> 汇报数据 -> 团队回顾 -> 识别瓶颈 -> 形成改进项 -> 判断回流 -> 产出纪要

**DoD 评估**：
- 读取 DoD 定义，收集实际产出，逐项对照检查
- 形成对照表（通过/未通过/部分通过）
- 对未通过项给出处理建议

#### 3.3.4 标准执行工作流

每次处理一份结构化工作输入时，按以下顺序执行：

1. 识别场景与选择入口
2. 建立处理链（trace_id）
3. 判断阶段
4. 检查输入
5. 执行一轮追问（或说明无需追问）
6. 执行分流
7. 执行回写
8. 回核主事实源
9. 执行通知
10. 判断下一流程
11. 生成审计日志
12. 更新运行状态

#### 3.3.5 允许动作

- 判断当前阶段
- 校验输入是否具备继续处理基础
- 发起一轮必要追问
- 做分流判断
- 生成回写计划
- 生成通知摘要
- 生成下一流程结论
- 生成审计日志
- 更新运行状态快照
- 主持标准会议
- 评估 DoD

#### 3.3.6 禁止越权事项

- 在planning阶段代替 PO 进行价值优先级拍板
- 擅自改变项目边界
- 擅自从普通状态切换到连续短 Sprint
- 在关键信息缺失时强行猜测并继续推进
- 把局部失败伪装为完全完成
- 跳过 Review 或 Retrospective
- 在阻断条件未解除时继续推进

### 3.4 脉冲小队 (Pulse Team, PT) -- 【人类 / AI / 人机混合】

- **核心定位**：脉冲的执行者。
- **职责**：5-9 人的固定团队（AI 可视作独立成员）。自我组织、自驱动，全职工作。可以是纯人类借助 AI 工具，也可以是直接引入 AI 成员独立认领任务。
- **统一约束**：当 Pulse Team 中存在 AI Agent 时，这些 Agent 必须遵循框架的统一执行契约，能够接收 SIS、理解任务边界、回写状态并推动 Backlog 流转。

## 4. 六大核心事件 (Events)

### 4.1 待办事项整理 (Backlog Grooming)

- **形态**：PO 和 PC 整理子任务，将结果以**结构化文档/指令集**输出给 Aida。Aida 给出评估反馈，PO 负责澄清模糊点。
- **输出**：更新后的 Backlog、未决议题记录、更新后的 manifest（PCB 成型后同步记忆）。

### 4.2 脉冲计划会议 (Sprint Planning)

- **形态**：PO 讲解最高优先级需求，团队估算工作量并认领。**所有结论必须文档化输出到 Backlog。**
- **AI 捷径**：如果 Backlog 足够完善且开发主力为 AI，PO 可直接委托 Aida 根据优先级自动生成短脉冲并开始推进。
- **输入**：Backlog、未决议题、上一轮 Retrospective 纪要（如有）。
- **主持流程**：
  1. 开场与范围确认（先咨询未决议题进度，短 Sprint 无视）
  2. 候选收集与呈现
  3. 三级收敛（正式输入 / 候补项 / 暂缓项）
  4. 执行顺序确认
  5. 产出启动文档
  6. 回写资产
- **PO 介入点**：三级收敛和顺序确认必须由 PO 决策。

### 4.3 脉冲执行同步 (Pulse Execution Sync) -- 【取代每日站会】

- **定位**：取代传统 Scrum 的每日站会。因为 AidaPulse 工作效率远高于传统 Scrum，原站会频率太低且固定时间不灵活。
- **发生阶段**：Sprint In Progress 期间，贯穿整个执行过程。
- **形态**：取消定点会议。改为**"事件驱动"**的异步状态同步机制。Aida 在事件发生时即时广播并 @ 相关人员。
- **任务分配**：长 Sprint 由 Aida 与 PO 共同决定每个 Backlog 项的负责人/agent，并行执行并追踪各任务进度（agent 自动获取任务，人类负责人通过输入与交付物推进到「待检查」由 Aida 做 DoD 关闭）；短 Sprint 由 Aida 自行将任务交给 agent，按依赖关系并行/串行执行并追踪进度。
- **DoD 时机**：每个任务完结后立即做 DoD 检查（不等 Sprint Completed 阶段），Sprint Completed 阶段再做一次总体复查。
- **触发条件**：
  - 任务执行完成通知
  - 资源告警
  - 风险通告
  - 出现卡点需要人工清障
  - SIS 执行状态更新
- **与反思会的关系**：Pulse Execution Sync 的事件日志作为 Retrospective 的决策辅助依据。
- **输出**：Pulse Execution Sync 事件日志，作为审计和反思的依据。

### 4.4 评审会议 (Sprint Review)

- **形态**：以"用户故事是否交付可用软件"为标准。
- **双轨制**：
  - **常规迭代**：保留传统形式，向利益相关者演示。
  - **短脉冲**：由 Aida 自行自动化测试和验收。通过后，只要 Backlog 充足，自动开启下一次脉冲交付。
- **主持流程**：
  1. 开场与范围确认
  2. 回顾 Sprint 原始承诺
  3. Aida 汇报完成情况
  4. 审查式清单（目标审查、交付物审查、Aida 表现审查、一致性审查、风险审查）
  5. PO 反馈与认可判断
  6. Backlog 与状态处理
  7. 决定下一阶段（检查 Backlog 池是否空，空则询问 PO 是否交付项目）
- **PO 介入点**：PO 反馈与认可判断必须由 PO 给出正式判断。

### 4.5 反思与进化会议 (Sprint Retrospective) -- 【可选】

- **触发条件**：Aida 觉得 Sprint 中有做的不好的、需要讨论的问题（未完成、效果不理想等），通知 PO 建议开启反思会。PO 认可后才走此流程。
- **形态**：Aida 提前输出可视化报告。团队总结"开始做、继续做、停止做"的事项。
- **核心使命**：**必须将迭代中验证极好的 AI 提示词、工作流或代码规范，抽象沉淀为 `SKILL`（如 SKILL.md）**。以此不断为整个系统和开发框架赋能。
- **输入**：Review 报告、审计轨迹、**Sprint 中的异步广播事件日志**（作为决策辅助依据）。
- **主持流程**：
  1. 开场与范围确认
  2. Aida 汇报过程数据（含异步广播事件统计）
  3. 团队回顾（好/不好）
  4. 识别瓶颈
  5. 形成改进项
  6. 判断回流方向
  7. 产出反思纪要
- **PO 介入点**：团队回顾和回流判断需要 PO 给出反馈和确认。
- **无阻断条件**：未形成有效结论时，把问题作为待完善项加入 Backlog，不需要卡点。

### 4.6 项目交付 (Project Delivery)

- **触发**：Review 阶段检查 Backlog 池已空时，询问 PO 是否交付项目。
- **分支**：PO 否决 -> 进入新一轮 Planning；PO 同意 -> Aida 生成项目报告并询问 PO 意见。
- **交付资产**：PO 同意后交付项目产品、项目报告、evolution_log 等项目资产。

## 5. 十二条基本原则 (Principles)

1. **最高目标**：通过尽早和持续地交付有价值的软件来满足客户。
2. **拥抱变更**：欢迎对需求提出变更（即使在开发后期），善用变更帮助客户获得竞争优势。
3. **脉冲式交付**：不断交付可用的软件，周期越短越好（借助 AI，周期可缩短至天甚至小时）。
4. **需求探索**：在迭代之间，始终追求更好、更准确的产品需求探索。
5. **全面赋能**：毫无保留地用好 AI 工具，为系统架构、产品设计和开发过程全面赋能。
6. **沟通基石**：无论是人类团队内部，还是人与 AI 之间，**最可靠的沟通方式是结构化文档和看板**。
7. **衡量标准**：可用的软件是衡量进度的首要指标。
8. **可持续开发**：项目方、人类开发人员、AI 和用户应能保持恒久、稳定的进展速度，不透支人类精力。
9. **技术卓越**：对技术的精益求精以及对设计的不断完善将提升敏捷性。
10. **简洁为本**：尽最大可能减少不必要的工作，这是一门艺术（将繁杂琐事交给 AI）。
11. **自组织**：最佳的架构、需求和设计，出自于高度自组织的人机协同团队。
12. **反省与沉淀**：团队定期反省如何更有效，调整行为，并将经验沉淀为系统级 `SKILL`。

## 6. 通用业务准则 (Global Business Rules)

- **人机协作原则**：所有任务应优先考虑 AI 自动化，人类介入点应聚焦于高层决策、复杂问题解决和创造性工作。PO 作为唯一必须由人类担任的商业价值锚点。
- **文档结构化**：所有需求、设计和知识沉淀必须以结构化、机器可读的格式（如 SIS、PCB）存储，同时提供人类可读的视图。结构化文档和看板是人机沟通的核心基石。
- **自动化优先**：测试、部署、监控、报告等环节应尽可能自动化，减少人工干预。
- **持续学习与进化**：团队和系统应通过 SKILL 沉淀机制，不断从实践中学习和优化。每个 Sprint 的反思结论都应争取回流为规则或 SKILL 候选。
- **透明度**：所有项目状态、进度、风险和决策过程应保持高度透明，通过审计日志、状态快照和异步通知呈现。
- **流程正义**：在任何时刻都明确当前所处阶段、当前允许做什么、不允许跳过什么，以保证框架可治理、可追踪、可复盘。

## 7. Aida 架构定义 (Architecture)

> **本节为概要引用，详细设计见独立文档。**

### 7.1 五层分层设计

Aida 不是"一个大模型包打天下"，而是五层职责分层：

| 层级 | 名称 | 职责 |
|------|------|------|
| L1 | 治理约束层 | 为 Aida 提供不可越过的规则边界，定义什么能做、什么不能做、什么必须阻断 |
| L2 | 流程编排层 | 根据当前阶段和状态，编排工作模块的执行顺序 |
| L3 | 工作模块层 | 会前准备、会议输入处理、分流沉淀、回写通知、会议主持、DoD 评估、Pulse Execution Sync 等具体能力模块 |
| L4 | 协议与资产层 | Backlog / SIS / PCB / 表单 / 未决议题池的读写网关，上下文按需装载 |
| L5 | 审计与评估层 | 审计日志留痕、审查支持 |

### 7.2 架构原则

- **架构正确优先于原型速度**：原型机可以简陋，但架构不能临时拼凑
- **上下文按需装载**：每个模块只装载完成当前任务所需的最小上下文
- **模块可独立演进**：新增 Agent 或 Skill 时不应要求重写整个 Aida
- **流程能力与价值决策分离**：Aida 管流程，PO 管价值

## 8. 记忆系统架构 (Memory System)

> **本节为概要引用，详细设计见独立文档。**

### 8.1 设计原则

- **文件驱动，不做数据库**：所有记忆数据以 Markdown 文件形式存储
- **最小可用，不做知识库**：只存"跨会话恢复工作状态"所需的最小信息
- **人类可读优先**：所有记忆文件优先保证人类可直接阅读和理解

### 8.2 四层记忆模型

| 层级 | 文件 | 职责 | 回答的问题 |
|------|------|------|----------|
| L1 | `memory/manifest.md` | 恢复清单 | "新会话第一件事读什么？按什么顺序装载？" |
| L2 | `memory/state.md` | 状态快照 | "当前在哪个 Sprint、哪个阶段、哪个任务？" |
| L2.5 | `memory/context_cache.md` | 上下文缓存 | "关键文档的精简摘要是什么？" |
| L3 | `memory/decisions.md` | 决策日志 | "最近发生了什么关键决策？为什么到了当前状态？" |

### 8.3 记忆原则

- **记忆与实际状态不一致时**，以实际状态为准并立即更新记忆，同时暴露不一致点
- **记忆分层职责不重叠**：L1 管"恢复顺序"，L2 管"当前状态"，L3 管"历史决策"
- **L1 是 L2 的恢复入口**，L2 是 L3 的查询索引

## 9. 独立运行能力 (Autonomous Operation)

### 9.1 核心原则

Aida 能够脱离长对话上下文，依靠项目过程文档和标准 IO 独立主导各阶段工作。

### 9.2 Aida 运行断言

1. **思考依据优先级**：产品资产 > 会话上下文 > 记忆 > 建设资产
2. **总能根据记忆知道项目阶段和状态**
3. **即使没有会话上下文，也能通过记忆知道在做什么项目、该做什么工作**（但不一定知道具体怎么做）
4. **不知道具体怎么做时，总能从建设资产（SIS 实例）和产品资产（rule）找到参考**
5. **永远知道下一步该做什么**（通过检查表和记忆）
6. **能从建设资产总结出有价值的过程资产作为以后其他类似项目的参考**

### 9.3 场景驱动输入契约

Aida 的主输入不是单一模板，而是**结构化工作输入**。处理前必须先判断当前属于哪类工作场景：

| 场景类型 | 适用情况 |
|---------|---------|
| 会议型输入 | 正式会议结束后的结构化处理 |
| 非会议型 Sprint 收尾输入 | 基于既有成果资产做 Sprint 收尾 |
| 审查型输入 | Review / Audit Review / Critic Review |
| 反思型输入 | Retrospective 流程反思与改进项收敛 |
| 短脉冲事件型输入 | 短 Sprint 中的事件驱动收束 |

### 9.4 阶段驱动自主行为

| 当前阶段 | Aida 自主动作 |
|----------|-------------|
| `Planning Input Ready` | 整理候选清单 -> 发起 Planning 或转项目交付 |
| `Planning Completed` | 确认正式输入 -> 按顺序启动执行 |
| `Sprint In Progress` | 推进当前任务 -> 完成后标记 -> 启动下一个（每个任务完结后立即 DoD） |
| `Sprint Completed` | 检查交付完整性 -> 总体 DoD 复查 -> 发起 Review |
| `Review Passed` | 检查是否需要 Retrospective -> 发起或跳过 |
| `Retrospective Completed` | 整理输入 -> 发起下一轮 Planning |
| `项目交付` | 生成项目报告 -> 询问 PO 意见 |
| `*_blocked` | 检查阻断是否解除 -> 若未解除则等待 |

### 9.5 自主推进边界

不得自主做的事情：
- 代替 PO 决定 Sprint 范围
- 擅自开启短 Sprint 模式
- 跳过 Review 或 Retrospective
- 在阻断条件未解除时继续推进
- 连续推进超过 3 个任务且无重大决策点时，不停下来向 PO 同步进度

## 10. 流程守门规则 (Flow Guard)

> **本节为概要引用，详细设计见独立文档。**
>
> **设计原则**：系统不需要过多卡点。只有在最基础的准入条件不满足时才硬阻断，其他阶段的问题通过流程自身消化（如回流 Backlog、补写报告等）。

### 10.1 守门机制

- **Backlog Grooming**：硬阻断。缺少 PCB / Backlog / 未决议题时阻断，Aida 按模板自动生成最小化资产并准备问卷加速收敛。
- **Planning**：仅"无任务池"为阻断条件（PO 确认无新任务=项目完成）。其他情况直接继续 Planning。
- **Sprint**：无阻断条件。遇到问题通过异步广播事件通知，由 PO 决定是否介入。
- **Review**：无主动阻断。未通过项回流到下次 Planning 或反思会。结论必须写，没写自己补。
- **Retrospective**：无主动阻断。未形成有效结论则加入 Backlog。
- **Planning Input Ready**：无阻断。只要有 Backlog 就可以进入 Planning（Backlog 燃尽则转项目交付）。
- **项目交付**：无阻断。PO 意见决定去向（否决进新 Planning，同意交付齐全）。

### 10.2 短 Sprint 准入

短 Sprint = Aida 获得 PO 权限后，自主走 3+4+5+6+7+8 完整 Sprint 流程（授权次数/边界受 AS-8 约束，事件流同步 PO）。

短 Sprint 的"短"体现在**时间维度**上，不是限制任务数量。因为全部采用 AI 开发，Aida 可全程自主检查评估，可连续开启，执行效率高。

准入条件（全部满足）：
- PO 明确授权
- Backlog 明确
- 高内聚的需求集合（**不限制任务数量**）
- AI 可自主评估的 DoD

## 11. 资产分类模型 (Asset Model)

> 可执行细则（归类判定清单 / 边界 / 流转规则 / 违规处置）见 [G6 资产治理模型](../rules/G6_资产治理模型_待确认.md)。

### 11.1 两类资产

| 类型 | 定义 | 特征 | 示例 |

### 11.3 资产沉淀路径

建设资产经过多次项目验证后，可提炼为产品资产：
1. 在 Retrospective 中提案
2. 经 PO 确认后迁移
3. 从项目特定配置抽象为通用规则

## 12. 反面教材 (Anti-Patterns)

- **禁止**：Aida 成为唯一知识持有者，依赖隐性知识而非结构化文档。
- **禁止**：僵化地将 AI 任务塞入固定周期的 Sprint，忽视短 Sprint 脉冲的适用场景。
- **禁止**：产品资产依赖建设资产（违反单向依赖原则）。
- **避免**：人类 PO 频繁干预短 Sprint 脉冲的自动化执行，除非 Aida 发出明确警报。
- **避免**：AI 生成的代码或产出未经 DoD 检查和必要审计即合入主分支。
- **避免**：SKILL 技能库未能得到有效维护和更新，导致知识无法复用和系统无法进化。
- **避免**：把原型机误当作正式产品，在核心工作习惯未稳住前过度扩功能。
- **避免**：记忆系统与实际状态不一致时未及时纠偏。

## 13. 演进指标 (Evolution Metrics)

### 13.1 AI 渗透率 (AI Penetration Rate)

AI 渗透率用于衡量 AI 在整个 AidaPulse 框架中的参与比例和作用深度。它不是单一的代码生成比例，而是一个面向框架成熟度的综合性指标。

AI 渗透率提升意味着：

1. 更多角色职责可以在清晰边界内由 AI 承担。
2. 更多 Backlog 项可以通过 SIS 被 AI 正确理解和执行。
3. 更多流程节点可以在不失控的前提下自动流转。
4. 更多高质量经验可以被沉淀为 `SKILL` 并复用。

### 13.2 其他建议指标

- **脉冲周期时间**：单个脉冲从启动到验收完成所需的时间。
- **Backlog 流转效率**：需求从进入 Backlog 到完成闭环的平均时间。
- **Skill 沉淀率**：每个阶段沉淀出可复用 Skill 的数量与质量。
- **人类干预率**：本应自动流转的任务中，实际需要人类介入的比例。

## 14. 术语表 (Glossary)

| 术语 | 定义 |
| :--- | :--- |
| **AidaPulse** | 面向 AI 时代的脉冲式敏捷开发框架，强调高频迭代、拥抱变化、结构化协作与持续进化。 |
| **Aida** | 框架中的核心 AI 编排中枢（Aida Orchestrator），负责需求拆解、流程推进、状态跟踪、自动验收和知识沉淀。 |
| **PO** | Product Owner，产品负责人，AidaPulse 中唯一必须由人类担任的商业价值锚点。 |

| **PT** | Pulse Team，脉冲小队，执行具体交付任务的人类、AI 或人机混合团队。 |
| **PCB** | Project Context Blueprint，项目背景蓝图，项目的"长期记忆"，提供全局上下文、约束、历史决策和稳定事实。 |
| **SIS** | Structured Instruction Set，结构化指令集，框架中的主要任务数据形式，也是各类 AI Agent 的统一输入协议。 |
| **Backlog** | 产品待办列表，是所有需求进入执行前的统一入口和优先级管理载体。 |
| **SKILL** | 团队沉淀的可复用能力资产，通常表现为规范、提示词、工作流或可执行方法。 |
| **短脉冲 (Short Pulse)** | 在边界明确、AI 就绪度足够高时，由 Aida 驱动的高频短周期执行单元。 |
| **脉冲式交付** | AidaPulse 中的非固定周期迭代模式，由 Aida 根据任务明确度和 PO 授权动态触发和执行。 |
| **AI 渗透率** | 衡量 AI 在角色承担、任务执行、流程推进和知识沉淀中参与比例与深度的综合指标。 |
| **流程正义** | 在任何时刻都明确当前所处阶段、当前允许做什么、不允许跳过什么，以保证框架可治理、可追踪、可复盘。 |
| **审计日志 (Audit Trace)** | 记录 Aida 关键判断、关键动作和关键去向的证据链，作为后续评审和纠偏依据。 |
| **建设资产** | 项目执行过程中产生的具体实例和过程产出，项目特定、过程性、一次性。 |
| **产品资产** | 可复用的框架级规则和方法论，通用、稳定、可跨项目复用。 |
| **记忆系统** | Aida 跨会话状态延续的文件系统，包含 L1 恢复清单、L2 状态快照、L2.5 上下文缓存、L3 决策日志。 |
| **工作流图** | 覆盖所有已定义阶段的 Mermaid 流程图 + 配套表格，Aida 凭此判断当前阶段和下一步动作。 |
| **进度检查表** | 从工作流图转化的可检查表格，Aida 用于自主推进时的自检。 |
| **DoD** | Definition of Done，完成定义，每个任务或 Sprint 的验收标准。 |
